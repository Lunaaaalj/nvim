1. KERNELS, NOT VENVS                                *nvim-notebooks-concept*

`:MoltenInit` does NOT browse for virtual environments. It lists the Jupyter
kernels registered on your machine. A venv is not automatically a kernel — you
register it once, and from then on it appears in the `:MoltenInit` picker.

  project venv  --(register once)-->  Jupyter kernel  --(:MoltenInit)-->  Molten

Molten reads the kernel list through `jupyter_client` in the Neovim host venv
`~/.virtualenvs/neovim`, so anything `jupyter kernelspec list` shows, Molten
sees too.

==============================================================================
2. REGISTERING A KERNEL                             *nvim-notebooks-register*

Use the `jkernel` helper (`~/.local/bin/jkernel`, already on `$PATH`): >
     cd /path/to/project
     source .venv/bin/activate     # or have .venv/ , venv/ , or env/ present
     jkernel add
<
`jkernel add`:
  1. Finds the venv — an activated $VIRTUAL_ENV first, else .venv/, venv/ or
     env/ in the current directory.
  2. Prompts for a kernel name (defaults to the folder name) and display name.
  3. Installs `ipykernel` into the venv if missing.
  4. Registers the kernel under `~/Library/Jupyter/kernels/`.

This is a one-time step per project: the kernelspec stores the absolute path
to that venv's Python, so everything you `pip install` in the venv is
available when you run cells.

Doing it manually (no helper): >
     source .venv/bin/activate
     pip install ipykernel
     python -m ipykernel install --user --name my-project \
       --display-name "My Project"
<
==============================================================================
3. MANAGING KERNELS (JKERNEL)                        *nvim-notebooks-jkernel*

  jkernel add          Register the current directory's venv (prompts for name)
  jkernel rm           Remove a kernel — interactive numbered picker
  jkernel rm <name>    Remove a kernel by name directly
  jkernel list         List registered kernels

Notes:
  - `jkernel` uses the Neovim host's `jupyter`
    (`~/.virtualenvs/neovim/bin/jupyter`) so its list matches what Molten sees.
    Override with `NVIM_JUPYTER=/path/to/jupyter jkernel ...`.
  - The "Native kernel (python3) is not available" warning from
    `jupyter kernelspec list` is harmless — the host venv has no kernel of its
    own.

4. DAILY FLOW                                           *nvim-notebooks-flow*

1. Open your `.ipynb` or `.py` in Neovim. `.ipynb` is converted to markdown on
   the fly by jupytext.nvim, so a "cell" is a fenced ```python code block.
2. `<leader>mi` (:MoltenInit), then pick the kernel for this project.
3. Evaluate code:
     <leader>rc   Run the whole cell the cursor is in (auto-selects the
                  enclosing ```python fence — the fast path)
     <leader>rr   Re-evaluate the current cell
     <leader>r    (visual) Evaluate an arbitrary visual selection
     <leader>e    Evaluate operator (e.g. <leader>e then a motion)

   Bulk execution (like VSCode run-all / above / below):
     <leader>ra   Run all cells, top to bottom
     <leader>rk   Run every cell above the current one (k = up)
     <leader>rj   Run the current cell and everything below (j = down)

   Cells run in order: the kernel queues evaluations, so outputs land in the
   right cells even though the requests fire at once. If the cursor is in prose
   between cells, the split falls on the cursor line.
4. Manage output:
     <leader>os   Open the output pane (see |nvim-notebooks-pane|)
     <leader>ot   Toggle the output pane
     <leader>oh   Close the output pane
     <leader>md   Delete the cell

Cells without inline images show their results as virtual text (e.g. in
Alacritty).

5. OUTPUT PANE                                          *nvim-notebooks-pane*

Output does not use a floating window. It goes to a docked pane in the
right-hand column, stacked *above* the REPL terminal when one is open
(`<leader>tR` / `<leader>tp`), so the layout reads like RStudio:

    +----------------------+-----------+
    |                      | - output -|
    |   report.qmd         |  <plot>   |
    |                      | mean:4.21 |
    |                      +-----------+
    |                      | R REPL    |
    +----------------------+-----------+

    <leader>os   Open the pane and focus it (refreshes to the current cell)
    <leader>ot   Toggle the pane
    <leader>oh   Close the pane

It refreshes itself after every evaluation: <leader>rc, <leader>ra,
<leader>rk, <leader>rj, <leader>rr and visual <leader>r all update it.

Text results still show inline under the cell as virtual text; plots do not
(`molten_image_location = "float"`), so figures appear only in the pane
instead of pushing your code around.

Opening a REPL terminal (<leader>tR / <leader>tp / <leader>tN) while the pane
is up moves it UNDER the pane instead of adding a third column, so the layout
above holds whichever you open first. <leader>th (horizontal panel) and
<leader>tf (float) are left where you asked for them.

Colours ~

The pane is transparent like every other window, so it takes the terminal's
colour and opacity. Plots instead get a solid white background baked into the
image: matplotlib's Jupyter backend saves figures transparent, and the Kitty
protocol composites them onto whatever is behind, which makes dark axes
unreadable. To change these: >
     require("defaults.molten_pane").plot_background = "#eeeeee"
     vim.api.nvim_set_hl(0, "MoltenPaneNormal", { bg = "#1b1b1b" })
<
How it works ~

Implemented in `lua/defaults/molten_pane.lua`.

  - Text. Molten only builds a cell's output buffer while rendering its float,
    so a refresh runs MoltenShowOutput, copies that buffer, then runs
    MoltenHideOutput — all in one callback. Neovim never redraws in between,
    so the float is never visible. The grab runs in the notebook's window, so
    it keeps working while the cursor sits in the REPL below.
  - Plots. Molten writes each figure to a temp PNG and binds the image to the
    *float's* window, which is why plots don't follow the buffer elsewhere.
    The pane reads those image objects' paths from image.nvim, flattens each
    PNG onto the background colour with ImageMagick (already required by
    image.nvim), and renders its own copies bound to the pane's window.
  - Size. image.nvim's max_width/max_height are global, so pane plots were
    capped at the max_height set for inline output. The pane opts out and
    scales each figure to fill the pane instead.

Output is asynchronous, so a refresh after a run polls on Molten's own status
header (On Hold / Running -> Done / Failed) every 500ms and stops as soon as
the cell settles. That is the only repeating work, and only while a cell is
pending (hard cap 2 minutes).

6. PLOTS / IMAGES                                     *nvim-notebooks-images*

Inline images only work in terminals speaking the Kitty graphics protocol
(Kitty / WezTerm / Ghostty). `lua/plugins/molten.lua` detects the terminal at
startup:

  - Capable terminal -> uses image.nvim, plots render inline.
  - Alacritty (the usual setup) -> molten_image_provider = "none", output is
    virtual text. View plots externally:
      <leader>oi       :MoltenImagePopup     (external image viewer)
      <localleader>mx  :MoltenOpenInBrowser

7. TROUBLESHOOTING                                   *nvim-notebooks-trouble*

Kernel not in `:MoltenInit` ~
  It isn't registered. Run `jkernel add` in the project, or check
  `jkernel list`.

`:MoltenInit` errors about remote plugins ~
  Run `:UpdateRemotePlugins` and restart Neovim (required after installing or
  updating molten-nvim).

`jupytext` / `pynvim` not found ~
  The Neovim Python host venv `~/.virtualenvs/neovim` is missing deps; it needs
  `pynvim`, `jupyter_client`, `jupytext`. See the Molten section of CLAUDE.md.

Wrong packages at runtime ~
  The kernel points at a specific venv. If you `pip install`ed into a different
  environment, install into the venv the kernel was registered from (or
  re-register it).

8. R / QUARTO                                         *nvim-notebooks-quarto*

`.qmd` (Quarto) documents get two things, from two different plugins:

  - LSP-in-chunks — quarto-nvim + otter.nvim (lua/plugins/quarto.lua) give
    diagnostics/completion/hover PER LANGUAGE inside each chunk (an {r} chunk
    gets R's LSP, a {python} chunk gets Python's). Editing support only, does
    not run anything.
  - Execution — still goes through Molten, exactly like .ipynb/.py.
    molten_cells() in lua/defaults/keymaps.lua recognizes both plain jupytext
    fences (```python) and Quarto's curly-brace chunk headers (```{r},
    ```{python}), so <leader>rc/ra/rk/rj work unchanged in .qmd files.

Registering R as a kernel ~
  Unlike Python, R has no per-project venv concept here — IRkernel
  registration is a ONE-TIME, MACHINE-WIDE step, not something `jkernel`
  handles: >
     install.packages("IRkernel")
     IRkernel::installspec()
<
  After that the R kernel shows up in <leader>mi (:MoltenInit) alongside any
  Python kernels — pick it the same way. <leader>tR opens a plain, persistent
  R REPL terminal (same pattern as <leader>tp/<leader>tN) for work outside
  Molten cells.

Preview ~
     <leader>op   :QuartoPreview      Run `quarto preview`, open/refresh a
                                       browser tab with live reload on save
     <leader>oP   :QuartoClosePreview Stop the preview

  This renders the whole document (all chunks, any language), unlike
  per-cell Molten output.

Plots ~
  The Alacritty-vs-Kitty-protocol image handling from section 5 is generic —
  it applies to R plots exactly like Python ones, no separate mechanism.
