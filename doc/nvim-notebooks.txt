1. PICKING A KERNEL                                   *nvim-notebooks-kernel*
                                                                    *:Kernel*

You pick a Python interpreter or environment, as in VS Code, not a
registered Jupyter kernel. There is no registration step
(lua/molten_kernels.lua).

Usually you don't pick at all. The first <leader>rc / <leader>ra / <leader>e
in a notebook starts a kernel by itself, from the first of these that
applies:
  1. the interpreter this file used last time;
  2. the one this project used last (the default for new notebooks in it);
  3. the project's only venv (.venv/, venv/, any dir with a pyvenv.cfg from
     the file's folder up to the project root, or a poetry / pipenv env
     named after the project);
  4. for an R-only .qmd, the only registered R kernel.
If it still can't tell, it opens the picker.

<leader>mi or :Kernel opens the picker. It lists the active $VIRTUAL_ENV /
$CONDA_PREFIX, project envs (★), ~/.virtualenvs/*, conda envs, pyenv
versions, uv-managed Pythons and the system Pythons, then every registered
kernel (IRkernel, old `jkernel` ones). The current choice is marked ●. It
also offers "+ Create .venv" (uv if installed, pip seeded so %pip works)
when the project has none, and "Enter interpreter path…".

:Kernel {path}      Use the Python at {path} (or in env dir {path}) directly.

If the env has no ipykernel, you get one confirmation, then it is installed
(`uv pip install`, else `python -m pip install`). Interpreters that refuse
installs (Homebrew, uv's own Pythons: PEP 668) offer to create a project
.venv from them instead.

The kernel runs in the notebook's folder, so relative paths and local
imports behave as in Jupyter. The env's bin is first on its PATH, so
`!pip install x` and subprocesses use that env. The statusline shows the
attached kernel.

<leader>mI is the raw :MoltenInit (registered kernels only). Use it to
attach a SECOND kernel to a buffer; switching with <leader>mi replaces the
attached one.

2. HOW IT WORKS                                        *nvim-notebooks-specs*

Molten can only start kernelspecs. For the chosen interpreter the module
writes one to stdpath("data")/molten/kernels/nvim-<env>-<hash>/ (one per
interpreter + notebook folder) and runs :MoltenInit with it. That directory
is put on $JUPYTER_PATH before the Python host starts. ~/Library/Jupyter is
untouched, so `jupyter kernelspec list`, VS Code and JupyterLab never see
these specs. Specs whose interpreter is gone, or that went unused for 30
days, are pruned when the picker opens. Choices are remembered in
stdpath("state")/molten_kernels.json.

3. REGISTERED KERNELS (OPTIONAL)                    *nvim-notebooks-register*
                                                     *nvim-notebooks-jkernel*

You only need these for kernels that aren't a Python env, such as R
(|nvim-notebooks-quarto|), or to share a kernel with other Jupyter
frontends. The `jkernel` helper (~/.local/bin/jkernel) still works:

  jkernel add          Register the current directory's venv (prompts for name)
  jkernel rm [name]    Remove a kernel
  jkernel list         List registered kernels

By hand: >
     .venv/bin/python -m pip install ipykernel
     .venv/bin/python -m ipykernel install --user --name my-project \
       --display-name "My Project"
<

4. DAILY FLOW                                           *nvim-notebooks-flow*

1. Open your `.ipynb` or `.py` in Neovim. `.ipynb` is converted to markdown on
   the fly by jupytext.nvim, so a "cell" is a fenced ```python code block.
2. Run a cell (<leader>rc): the kernel starts by itself
   (|nvim-notebooks-kernel|). <leader>mi switches to another one.
3. Evaluate code:
     <leader>rc   Run the whole cell the cursor is in (auto-selects the
                  enclosing ```python fence — the fast path)
     <leader>rr   Re-evaluate the current cell
     <leader>r    (visual) Evaluate an arbitrary visual selection
     <leader>e    Evaluate operator (e.g. <leader>e then a motion)

   Bulk execution (like VSCode run-all / above / below):
     <leader>ra   Run all cells, top to bottom
     <leader>rk   Run every cell above the current one (k = up)
     <leader>rj   Run the current cell and everything below (j = down)

   Bulk runs only send cells in the kernel's language (a ```bash example in
   a Markdown cell is skipped). Cells run in order: the kernel queues evaluations, so outputs land in the
   right cells even though the requests fire at once. If the cursor is in prose
   between cells, the split falls on the cursor line.
4. Manage output:
     <leader>os   Open the output window
     <leader>oh   Hide output
     <leader>md   Delete the cell

Cells without inline images show their results as virtual text (e.g. in
Alacritty).

5. PLOTS / IMAGES                                     *nvim-notebooks-images*

Inline images only work in terminals speaking the Kitty graphics protocol
(Kitty / WezTerm / Ghostty). `lua/plugins/molten.lua` detects the terminal at
startup:

  - Capable terminal -> uses image.nvim, plots render inline.
  - Alacritty (the usual setup) -> molten_image_provider = "none", output is
    virtual text. View plots externally:
      <leader>oi       :MoltenImagePopup     (external image viewer)
      <localleader>mx  :MoltenOpenInBrowser

6. TROUBLESHOOTING                                   *nvim-notebooks-trouble*

"Molten isn't registered" ~
  Run `:UpdateRemotePlugins` and restart Neovim (required after installing or
  updating molten-nvim).

An env is missing from the picker ~
  Envs are found by their pyvenv.cfg (venvs), conda-meta/ (conda) or the
  usual install dirs. Use "Enter interpreter path…" or `:Kernel {path}`.

Installing ipykernel failed ~
  The error is in the notification. Offline or behind a proxy, install it
  yourself (`.venv/bin/python -m pip install ipykernel`) and pick again.

`jupytext` / `pynvim` not found ~
  The Neovim Python host venv `~/.virtualenvs/neovim` is missing deps. It
  needs `pynvim`, `jupyter_client` and `jupytext`, plus `pillow` for
  :MoltenImagePopup, `nbformat` for :MoltenImportOutput/:MoltenExportOutput,
  and `cairosvg` for SVG plots: >
     ~/.virtualenvs/neovim/bin/pip install pillow nbformat cairosvg
<
Wrong packages at runtime ~
  The kernel runs the env shown in the statusline; `%pip install x` in a cell
  installs into it.

7. R / QUARTO                                         *nvim-notebooks-quarto*

`.qmd` (Quarto) documents get two things, from two different plugins:

  - LSP-in-chunks — quarto-nvim + otter.nvim (lua/plugins/quarto.lua) give
    diagnostics/completion/hover PER LANGUAGE inside each chunk (an {r} chunk
    gets R's LSP, a {python} chunk gets Python's). Editing support only, does
    not run anything.
  - Execution — still goes through Molten, exactly like .ipynb/.py.
    molten_cells() in lua/defaults/keymaps.lua recognizes both plain jupytext
    fences (```python) and Quarto's curly-brace chunk headers (```{r},
    ```{python}), so <leader>rc/ra/rk/rj work unchanged in .qmd files.

Registering R as a kernel ~
  Unlike Python, R has no per-project venv concept here — IRkernel
  registration is a ONE-TIME, MACHINE-WIDE step: >
     install.packages("IRkernel")
     IRkernel::installspec()
<
  After that the R kernel shows up in <leader>mi after the Python
  interpreters, and an R-only .qmd picks it by itself. <leader>tR opens a plain, persistent
  R REPL terminal (same pattern as <leader>tp/<leader>tN) for work outside
  Molten cells.

Preview ~
     <leader>op   :QuartoPreview      Run `quarto preview`, open/refresh a
                                       browser tab with live reload on save
     <leader>oP   :QuartoClosePreview Stop the preview

  This renders the whole document (all chunks, any language), unlike
  per-cell Molten output.

Plots ~
  The Alacritty-vs-Kitty-protocol image handling from section 5 is generic —
  it applies to R plots exactly like Python ones, no separate mechanism.
