1. KERNELS: AUTOMATIC                                *nvim-notebooks-concept*

You don't register anything. The first run key in a buffer without a kernel
(<leader>mr, <leader>ma, <leader>me, ..., or <leader>mi on its own) picks one
and starts it (`lua/notebook/kernel.lua`):

  Python    A kernelspec generated for the project's interpreter, the same
            one pyright, the debugger and <leader>tp use (|nvim-config-pyenv|:
            `.venv`/`venv`/`env` upward, then $VIRTUAL_ENV / $CONDA_PREFIX).
            - venv has `ipykernel` -> its Python runs the kernel directly.
            - otherwise -> `uv run --with ipykernel` layers an ephemeral
              ipykernel over the venv: the venv's packages import, nothing is
              installed into it (needs `uv`).
            Without a project venv, a Python kernel named in the notebook's
            metadata is used if it's registered, else the system Python.
  R, Julia  The kernel named in the notebook's metadata (`kernelspec:` in the
            front matter, or a .qmd's `jupyter: ir`), else the first
            installed kernel for the language (R = IRkernel's `ir`).

The language is the metadata's, else the cell being run's (an R chunk in a
.qmd that starts with Python starts R), else the first code fence's.

Working directory: the document's folder, as Quarto/knitr and Jupyter run
code, so `source("../R/x.R")` or `read_csv("data.csv")` work. R starts in the
project root (nearest `renv.lock`/`.Rprofile`, so renv activates) and then
`setwd()`s there. In a renv project IRkernel (installed machine-wide) isn't in
the project library: the kernel adds R's own libraries after the project's,
so project packages still win and only IRkernel and its deps come from them.

Starting never freezes Neovim for long: the kernel's command is checked first
in the background (`import ipykernel`, which also fills uv's cache; IRkernel
loads), and a failing one is reported without reaching Molten. A kernel that
still doesn't answer within 30 s is shut down (`:MoltenDeinit`). Why: until a
kernel answers, each Molten tick blocks Neovim for ~1 s, forever if the kernel
died. The usual 1-2 s boot after the check still stutters a little. Generated specs live in `stdpath("data")/jupyter/kernels`
(`py-<project>-<hash>`), reach Molten through $JUPYTER_PATH (set at startup,
so also visible to `jupyter kernelspec list` in :terminal), are refreshed on
every start and removed once their venv is gone. They never touch
`~/Library/Jupyter`.

Installing packages: with the uv layer, `%pip install` inside the kernel goes
to the ephemeral layer and is lost. Install into the venv from a shell
(`uv pip install --python .venv/bin/python pkg`, or the venv's pip) and
restart the kernel. With `ipykernel` in the venv, `%pip` installs there.

2. CHOOSING ANOTHER KERNEL                          *nvim-notebooks-register*

  <leader>mi    Start the automatic kernel (see above) and say which it is.
  <leader>mI    :MoltenInit picker: every kernel Jupyter knows, generated
                ones included, plus running kernels to share.

3. REGISTERED KERNELS (JKERNEL, OPTIONAL)            *nvim-notebooks-jkernel*

Not needed for Python projects any more. A registered kernel still appears in
<leader>mI, and is used automatically when a notebook without a project venv
names it. The `jkernel` helper (`~/.local/bin/jkernel`, not in this repo)
manages them in `~/Library/Jupyter/kernels`:

  jkernel add          Register the current directory's venv (prompts for name)
  jkernel rm [name]    Remove a kernel (picker without a name)
  jkernel list         List registered kernels

It uses the Neovim host's `jupyter` (`~/.virtualenvs/neovim/bin/jupyter`).
The "Native kernel (python3) is not available" warning from `jupyter
kernelspec list` is harmless: the host venv has no kernel of its own.

4. DAILY FLOW                                           *nvim-notebooks-flow*

1. Open a `.ipynb`, `.qmd`, `.Rmd`, or a `.py`/`.R` script with `# %%` cells.
   A `.ipynb` is converted on the fly by jupytext.nvim and opens as a Quarto
   buffer (|nvim-notebooks-ipynb|).
2. Run a cell with <leader>mr (or <leader>mn to run and advance). The first
   run starts the project's kernel (|nvim-notebooks-concept|); there is no
   kernel picker. The statusline shows the kernel, and "busy" while cells run.
3. Output is shown as virtual lines under the cell; the float stays closed
   until <leader>ms. Output windows are solid (a slightly tinted background,
   green/red border for success/failure) in transparent and solid mode.
   Cells run in order: Molten queues them, so outputs land in the right cells
   even though the requests fire at once.

                                                        *nvim-notebooks-keys*
Every key here is BUFFER-LOCAL: it exists only in notebook buffers (.ipynb,
.qmd, .Rmd, and .py/.R/.jl scripts with `# %%` cells; |nvim-notebooks-cells|).
The first run in a buffer starts its kernel (|nvim-notebooks-concept|).

Run ~
  <leader>mr    Run the cell under the cursor (visual: the selection)
  <leader>mn    Run the cell and move to the next (adds one at the end)
  <leader>ma    Run all cells
  <leader>mk    Run every cell above
  <leader>mj    Run this cell and everything below
  <leader>ml    Run the current line
  <leader>me    Run an operator (then a motion)
  <leader>mR    Re-run the cell Molten knows under the cursor
Cells ~
  ]c  [c        Next / previous cell ([c from inside a cell: its top)
  ij  aj        Text objects: the cell's code / with its fences (`yij`, `vaj`)
  <leader>mo    New cell below          <leader>mO    New cell above
Kernel ~
  <leader>mi    Start the project's kernel and say which it is
  <leader>mI    Pick a kernel (:MoltenInit)
  <leader>mx    Interrupt               <leader>mX    Restart
  <leader>mE    Run cells in the REPL terminal <-> a Molten kernel
                (|nvim-notebooks-repl|)
Output ~
  <leader>ms    Show / enter the output float     <leader>mh    Hide it
  <leader>mf    The cell's whole output in a scratch split
  <leader>md    Delete the cell's output
  <leader>mv    The last plot full size in a split
  <leader>mg    Image in the system viewer        <leader>mb    HTML in the browser
  <leader>mp    Plot paper: theme colours <-> white (|nvim-notebooks-images|)
Quarto (.qmd and notebooks) ~
  <leader>pv    PDF preview in the kitty split (quarto -> typst; visual: the
                selection), <leader>pF live follow, <leader>pk close
  <leader>op    Live-reload preview in a browser  <leader>oP    Stop it

                                                       *nvim-notebooks-cells*
What counts as a cell ~
  ```{r}, ```{python echo=false}   Quarto / R Markdown chunks, any language
  ```python, ```r, ```julia        plain fences, only these languages: a
                                   ```bash or ```text block in prose is never
                                   sent to the kernel (nor anything inside
                                   jupytext's `<!-- #region -->` markers)
  # %%                             percent scripts; `# %% [markdown]` cells
                                   are skipped, code above the first marker
                                   is a cell of its own
  Fence lines and `# %%` markers are dimmed. Formatting (format on save,
  <leader>cf) formats each cell with its language's formatter (conform's
  `injected`: ruff for Python, styler for R) and leaves prose alone.

                                                       *nvim-notebooks-ipynb*
Notebooks (.ipynb) ~
  The buffer holds jupytext's Markdown text (```python fences) with filetype
  `quarto`: otter.nvim gives each cell its language's LSP (pyright, ruff,
  R), and the Markdown-only tools (render-markdown, prettier, <leader>pv)
  stay out. jupytext's own "quarto" text format is not used: it turned the
  first `# Heading` into front matter and wrote it back into the notebook as
  a raw YAML cell.
  Outputs: when the notebook's kernel starts, the outputs saved in the file
  are loaded back (:MoltenImportOutput); every `:w` writes the outputs
  computed here into the `.ipynb` (:MoltenExportOutput), so they are there in
  Jupyter, on GitHub, and next time. Molten matches outputs to cells by their
  code, so a cell edited since it ran can't be matched and the export stops
  with a message (re-run it). Molten stores printed text as `text/plain`
  display data rather than a `stream`; it renders the same. Needs `nbformat`
  in the Neovim host venv.

                                                        *nvim-notebooks-repl*
Scripts: the REPL engine ~
  In a `.py`/`.R` script with `# %%` cells, the run keys send cells to the
  pinned REPL terminal (lua/terminals, the same one as <leader>tp / <leader>tR)
  instead of a Molten kernel; the statusline says "▷ IPython REPL".
  <leader>mE switches any notebook buffer between the two engines.
    Python  IPython on the project's interpreter (|nvim-config-pyenv|): the
            venv's own `ipython`, else an ephemeral one layered by
            `uv run --with ipython` (nothing installed), else plain python.
    R       radian if installed, else `R`. Your `.Rprofile` (the project's,
            for renv, else ~/.Rprofile) is still read.
  Cells go in as one paste; a REPL that is still starting gets them once it
  shows its first prompt.
  Plots: a Neovim :terminal can't show kitty images, so the REPLs save each
  plot as a PNG and Neovim opens it in an image split (reused for the next
  one; <leader>mv reopens it), on the plot paper. Python: a small matplotlib
  backend (`plt.show()`, and after every IPython input). R: after any command
  that changed the plot, so `plot()` then `lines()` both show.

Cells without inline images show their results as virtual text (e.g. in
Alacritty).

5. PLOTS / IMAGES                                     *nvim-notebooks-images*

Inline images only work in terminals speaking the Kitty graphics protocol
(Kitty / WezTerm / Ghostty). `lua/plugins/molten.lua` detects the terminal at
startup:

  - Capable terminal (kitty, the usual setup) -> uses image.nvim, plots
    render inline, sized to the cell height (retina screens get a higher
    figure dpi, so plots aren't half size).
      <leader>mv       The last plot full size in a split
  - Alacritty and others -> molten_image_provider = "none", output is
    virtual text. View plots externally:
      <leader>mg       :MoltenImagePopup     (external image viewer)
      <leader>mb       :MoltenOpenInBrowser

Plot paper ~
  <leader>mp toggles how plots are drawn (persisted, applies to the next plot,
  no kernel restart):
    theme   (default) the colorscheme's background, its foreground for text,
            axes and labels, a faint grid
    paper   black on white, like an exported notebook
  Kernels started by this config pick it up: Python through $MATPLOTLIBRC
  (matplotlib's defaults; a style you set yourself, `plt.style.use(...)`,
  seaborn themes, wins), R through `repr.plot.bg`, `par()` and the ggplot2
  theme. Every image is also flattened onto the paper before it's drawn, so
  a transparent figure (`savefig(transparent=True)`) never shows the terminal
  through it. Kernels you pick by hand from <leader>mI that weren't generated
  here only get the flattening.

6. TROUBLESHOOTING                                   *nvim-notebooks-trouble*

Wrong or no kernel picked ~
  `:PyEnv` shows the interpreter the buffer resolves to. "has no ipykernel
  and `uv` isn't installed": install uv, or `ipykernel` into the venv. A venv
  broken by a Homebrew upgrade is skipped with a warning; repair it with
  `python3 -m venv --upgrade <venv>`. <leader>mI picks any kernel by hand.

`:MoltenInit` errors about remote plugins ~
  Run `:UpdateRemotePlugins` and restart Neovim (required after installing or
  updating molten-nvim).

`jupytext` / `pynvim` not found ~
  `jupytext` is a uv tool: `uv tool install jupytext`. `pynvim` and
  `jupyter_client` belong in the Neovim Python host venv `~/.virtualenvs/neovim`
  (which is deliberately not on $PATH, see |nvim-config-pyenv|).

Wrong packages at runtime ~
  Check `:PyEnv`; install into that venv and restart the kernel (see the
  `%pip` note in |nvim-notebooks-concept|).

7. R / QUARTO                                         *nvim-notebooks-quarto*

`.qmd` (Quarto) documents get two things, from two different plugins:

  - LSP-in-chunks — quarto-nvim + otter.nvim (lua/plugins/quarto.lua) give
    diagnostics/completion/hover PER LANGUAGE inside each chunk (an {r} chunk
    gets R's LSP, a {python} chunk gets Python's). Editing support only, does
    not run anything.
  - Execution — goes through Molten, exactly like .ipynb and scripts, with
    the same keys (|nvim-notebooks-keys|): curly chunk headers (```{r},
    ```{python}) are cells like plain fences (|nvim-notebooks-cells|).

Registering R as a kernel ~
  Unlike Python, R has no per-project venv concept here — IRkernel
  registration is a ONE-TIME, MACHINE-WIDE step, not something `jkernel`
  handles: >
     install.packages("IRkernel")
     IRkernel::installspec()
<
  After that, R cells (```{r}, or an R notebook's metadata) start the `ir`
  kernel on the first run, no picker. <leader>tR opens a plain, persistent
  R REPL terminal (same pattern as <leader>tp/<leader>tN) for work outside
  Molten cells.

Preview ~
     <leader>op   :QuartoPreview      Run `quarto preview`, open/refresh a
                                       browser tab with live reload on save
     <leader>oP   :QuartoClosePreview Stop the preview

  This renders the whole document (all chunks, any language), unlike
  per-cell Molten output.

Plots ~
  The Alacritty-vs-Kitty-protocol image handling from section 5 is generic —
  it applies to R plots exactly like Python ones, no separate mechanism.
