1. KERNELS: AUTOMATIC                                *nvim-notebooks-concept*

You don't register anything. The first run key in a buffer without a kernel
(<leader>rc, <leader>ra, <leader>e, ..., or <leader>mi on its own) picks one
and starts it (`lua/notebook/kernel.lua`):

  Python    A kernelspec generated for the project's interpreter, the same
            one pyright, the debugger and <leader>tp use (|nvim-config-pyenv|:
            `.venv`/`venv`/`env` upward, then $VIRTUAL_ENV / $CONDA_PREFIX).
            - venv has `ipykernel` -> its Python runs the kernel directly.
            - otherwise -> `uv run --with ipykernel` layers an ephemeral
              ipykernel over the venv: the venv's packages import, nothing is
              installed into it (needs `uv`).
            Without a project venv, a Python kernel named in the notebook's
            metadata is used if it's registered, else the system Python.
  R, Julia  The kernel named in the notebook's metadata (`kernelspec:` in the
            front matter, or a .qmd's `jupyter: ir`), else the first
            installed kernel for the language (R = IRkernel's `ir`).

The language is the metadata's, else the first code fence's (```python,
```{r}). Generated specs live in `stdpath("data")/jupyter/kernels`
(`py-<project>-<hash>`), reach Molten through $JUPYTER_PATH (set at startup,
so also visible to `jupyter kernelspec list` in :terminal), are refreshed on
every start and removed once their venv is gone. They never touch
`~/Library/Jupyter`.

Installing packages: with the uv layer, `%pip install` inside the kernel goes
to the ephemeral layer and is lost. Install into the venv from a shell
(`uv pip install --python .venv/bin/python pkg`, or the venv's pip) and
restart the kernel. With `ipykernel` in the venv, `%pip` installs there.

2. CHOOSING ANOTHER KERNEL                          *nvim-notebooks-register*

  <leader>mi    Start the automatic kernel (see above) and say which it is.
  <leader>mI    :MoltenInit picker: every kernel Jupyter knows, generated
                ones included, plus running kernels to share.

==============================================================================
3. REGISTERED KERNELS (JKERNEL, OPTIONAL)            *nvim-notebooks-jkernel*

Not needed for Python projects any more. A registered kernel still appears in
<leader>mI, and is used automatically when a notebook without a project venv
names it. The `jkernel` helper (`~/.local/bin/jkernel`, not in this repo)
manages them in `~/Library/Jupyter/kernels`:

  jkernel add          Register the current directory's venv (prompts for name)
  jkernel rm [name]    Remove a kernel (picker without a name)
  jkernel list         List registered kernels

It uses the Neovim host's `jupyter` (`~/.virtualenvs/neovim/bin/jupyter`).
The "Native kernel (python3) is not available" warning from `jupyter
kernelspec list` is harmless: the host venv has no kernel of its own.

4. DAILY FLOW                                           *nvim-notebooks-flow*

1. Open your `.ipynb` or `.py` in Neovim. `.ipynb` is converted to markdown on
   the fly by jupytext.nvim, so a "cell" is a fenced ```python code block.
2. Run a cell. The first run starts the project's kernel
   (|nvim-notebooks-concept|); there is no kernel picker.
3. Evaluate code:
     <leader>rc   Run the whole cell the cursor is in (auto-selects the
                  enclosing ```python fence — the fast path)
     <leader>rr   Re-evaluate the current cell
     <leader>r    (visual) Evaluate an arbitrary visual selection
     <leader>e    Evaluate operator (e.g. <leader>e then a motion)

   Bulk execution (like VSCode run-all / above / below):
     <leader>ra   Run all cells, top to bottom
     <leader>rk   Run every cell above the current one (k = up)
     <leader>rj   Run the current cell and everything below (j = down)

   Cells run in order: the kernel queues evaluations, so outputs land in the
   right cells even though the requests fire at once. If the cursor is in prose
   between cells, the split falls on the cursor line.
4. Manage output:
     <leader>os   Open the output window
     <leader>oh   Hide output
     <leader>md   Delete the cell

Cells without inline images show their results as virtual text (e.g. in
Alacritty).

5. PLOTS / IMAGES                                     *nvim-notebooks-images*

Inline images only work in terminals speaking the Kitty graphics protocol
(Kitty / WezTerm / Ghostty). `lua/plugins/molten.lua` detects the terminal at
startup:

  - Capable terminal (kitty, the usual setup) -> uses image.nvim, plots
    render inline.
  - Alacritty and others -> molten_image_provider = "none", output is
    virtual text. View plots externally:
      <leader>oi       :MoltenImagePopup     (external image viewer)
      <localleader>mx  :MoltenOpenInBrowser

6. TROUBLESHOOTING                                   *nvim-notebooks-trouble*

Wrong or no kernel picked ~
  `:PyEnv` shows the interpreter the buffer resolves to. "has no ipykernel
  and `uv` isn't installed": install uv, or `ipykernel` into the venv. A venv
  broken by a Homebrew upgrade is skipped with a warning; repair it with
  `python3 -m venv --upgrade <venv>`. <leader>mI picks any kernel by hand.

`:MoltenInit` errors about remote plugins ~
  Run `:UpdateRemotePlugins` and restart Neovim (required after installing or
  updating molten-nvim).

`jupytext` / `pynvim` not found ~
  `jupytext` is a uv tool: `uv tool install jupytext`. `pynvim` and
  `jupyter_client` belong in the Neovim Python host venv `~/.virtualenvs/neovim`
  (which is deliberately not on $PATH, see |nvim-config-pyenv|).

Wrong packages at runtime ~
  Check `:PyEnv`; install into that venv and restart the kernel (see the
  `%pip` note in |nvim-notebooks-concept|).

7. R / QUARTO                                         *nvim-notebooks-quarto*

`.qmd` (Quarto) documents get two things, from two different plugins:

  - LSP-in-chunks — quarto-nvim + otter.nvim (lua/plugins/quarto.lua) give
    diagnostics/completion/hover PER LANGUAGE inside each chunk (an {r} chunk
    gets R's LSP, a {python} chunk gets Python's). Editing support only, does
    not run anything.
  - Execution — still goes through Molten, exactly like .ipynb/.py.
    molten_cells() in lua/defaults/keymaps.lua recognizes both plain jupytext
    fences (```python) and Quarto's curly-brace chunk headers (```{r},
    ```{python}), so <leader>rc/ra/rk/rj work unchanged in .qmd files.

Registering R as a kernel ~
  Unlike Python, R has no per-project venv concept here — IRkernel
  registration is a ONE-TIME, MACHINE-WIDE step, not something `jkernel`
  handles: >
     install.packages("IRkernel")
     IRkernel::installspec()
<
  After that, R cells (```{r}, or an R notebook's metadata) start the `ir`
  kernel on the first run, no picker. <leader>tR opens a plain, persistent
  R REPL terminal (same pattern as <leader>tp/<leader>tN) for work outside
  Molten cells.

Preview ~
     <leader>op   :QuartoPreview      Run `quarto preview`, open/refresh a
                                       browser tab with live reload on save
     <leader>oP   :QuartoClosePreview Stop the preview

  This renders the whole document (all chunks, any language), unlike
  per-cell Molten output.

Plots ~
  The Alacritty-vs-Kitty-protocol image handling from section 5 is generic —
  it applies to R plots exactly like Python ones, no separate mechanism.
